# BasketCoin — краткая спецификация смарт-контракта (черновик v0.4: лимит изменения индекса ±11%)

Статус: прототип для тестов. Прошёл внутреннюю проверку (см. `AUDIT_REPORT.md`), внешнего аудита не было, ни в одну сеть не деплоился.

Изменения v0.3 относительно v0.2 — в разделе 9, v0.4 — в разделе 10.
Solidity 0.8.24, OpenZeppelin 5.1.0, Foundry.

## 1. Архитектура
| Контракт | Роль |
|---|---|
| `BasketToken` (ERC20 + AccessControl) | Токен корзины. Сам залог не хранит. `mint`/`burn` может вызывать только адрес с ролью `MINTER_ROLE` (Vault). Эмиссия не ограничена. |
| `BasketVault` (Ownable2Step, Pausable, ReentrancyGuard, SafeERC20) | Хранит залог, ведёт реестр корзин `basketId → {токен, индекс, рабочая цена}`, принимает стейблы, минтит и выкупает токены. |
| `DateLib` | Перевод `block.timestamp` в дату по UTC (алгоритм civil_from_days, без внешних библиотек). |
| `IAggregatorV3` | Chainlink-совместимый интерфейс ценового фида стейбла. |

Сейчас есть одна корзина: `basketId = 1`, средний токен BasketCoin. Чтобы добавить токен под отдельную валюту, нужно развернуть ещё один `BasketToken`, выдать Vault роль `MINTER_ROLE` и вызвать `addBasket(id, token, initialIndex)`. Резервы учитываются отдельно по каждой паре «корзина + стейбл», поэтому корзины друг друга не обеспечивают.

## 2. Параметры
| Параметр | Значение |
|---|---|
| Оракул | только owner (ключ Антона) |
| Фиксация индекса `setIndex` | только 28-го числа по UTC и не чаще одного раза в календарный месяц; рабочая цена сбрасывается на новый индекс |
| Лимит изменения индекса | **±11% за одно обновление** от предыдущего зафиксированного индекса корзины (`MAX_INDEX_CHANGE_BPS = 1100`, константа). Границы включительно и округляются в сторону строгости: `min = ceil(old × 0,89)`, `max = floor(old × 1,11)`, поэтому диапазон никогда не шире ±11%. Отказ — `IndexChangeTooLarge(basketId, oldIndex, newIndex, minAllowed, maxAllowed)`. Revert не расходует попытку месяца: в тот же день можно повторить с допустимым значением. Стартовый индекс в `addBasket` лимитом не ограничен. Текущий диапазон — view `indexBounds(basketId)` |
| Рабочая цена `setWorkingPrice` | в пределах ±3% от последнего зафиксированного индекса; минт и выкуп идут по рабочей цене |
| Комиссия | 0,3% (30 bps) на минт и на выкуп, в стейбле, уходит на `feeRecipient` (казна, owner может сменить) |
| Минимальный минт | `minMintUsd`, owner меняет в диапазоне $50–$1000 включительно. **К чему применяется:** к сумме стейбла, *фактически поступившей* в Vault (для токенов с комиссией за перевод — после неё), *до* комиссии протокола 0,3%, оценённой по min(p, $1) с округлением вниз. Пример: при `minMintUsd = $50` депозит ровно 50 USDT проходит (в резерв 49,85 USDT), 49,999999 USDT — `BelowMinMint`. Если USDT стоит $0,99, нужно ≥ 50,505051 USDT. На выкуп минимум не распространяется |
| Стейблы | USDT и USDC добавляются в конструкторе; decimals читаются из токена (6); поддерживаются decimals 0–18 (проверка уже в `proposeStable`). Новый стейбл: `proposeStable` → `executeStable` не раньше чем через 9 дней (`cancelStable` отменяет) |
| Депег | цена стейбла берётся из фида, если он свежий и валиден, иначе из ручной цены owner'а. Если цена вне диапазона $0,95–$1,05 включительно, минт и выкуп блокируются только в этом стейбле. Когда цена возвращается в диапазон, блокировка снимается сама |
| Аварийная пауза | `pause`/`unpause` вызывает только owner; останавливает весь минт и выкуп |
| Буфер | 20% (`BUFFER_BPS = 2000`); возвращается при выкупе только при покрытии ≥ 140% |
| Уровни выкупа | ≥140% FULL / 115–140% STANDARD / <115% SUSPENDED (константы) |
| Пополнение резерва | `topUpReserve` — любой адрес, без минта |
| Owner | передача владения в два шага (`transferOwnership` → `acceptOwnership`); `renounceOwnership` отключён |

## 3. Формулы (индекс P — цена одного токена в USD; p — цена стейбла)
**Минт** (стейбл поступает в контракт, токены выдаются пользователю):
```
fee    = ceil(amount × 0,3%)      → казна (округление вверх, в пользу протокола)
net    = amount − fee             → резерв корзины в этом стейбле
netUsd = net × min(p, $1)
tokens = floor(net × 10^(18−dec) × min(p,$1) / (P × 1,2))   — одно округление (Math.mulDiv), вниз
```
Пример: 1000 USDT при P = $1 → комиссия 3 USDT, в резерв 997 USDT, пользователь получает 830,8333 BasketCoin. Обеспечение = 997 / 830,83 = 120%.

**Покрытие корзины**:
```
coverage = Σ по стейблам [ reserve_i × min(p_i, $1) ]  /  (totalSupply × P)
```
Стейблы оцениваются консервативно, по min(p, $1). Если `totalSupply = 0`, покрытие считается бесконечным (`type(uint256).max`) и уровень — FULL; выкупать в этом случае некому. Покрытие доступно через `collateralRatioBps(basketId)` в bps (12000 = 120%), уровень — через `redeemTier(basketId)`.

**Выкуп: три уровня.** Уровень определяется по покрытию *до* выкупа. Пороги — константы `FULL_REDEEM_COVERAGE_BPS = 14000` и `MIN_REDEEM_COVERAGE_BPS = 11500`; владелец их менять не может.

| Покрытие | Уровень | Выплата (usd) |
|---|---|---|
| ≥ 140% | FULL | tokens × P × 1,2 — залог вместе с буфером |
| от 115% (включительно) до 140% | STANDARD | tokens × P — без буфера. Выкуп доступен; сайт мягко предлагает подождать |
| < 115% | SUSPENDED | выкуп отклоняется с ошибкой `RedemptionSuspended(basketId, coverageBps, 11500)`. Блокировка снимается сама, как только покрытие снова ≥ 115% |

Пересчёт выплаты в стейбл:
```
gross = floor(tokens × P × k / (max(p,$1) × 10^(18−dec)))   — одно округление, вниз (k = 1,2 / 1,0)
fee   = ceil(gross × 0,3%),   пользователю: gross − fee (если 0 — ошибка ZeroAmount)
gross ≤ резерв этого стейбла в этой корзине
```

**Почему выкуп не ухудшает положение оставшихся держателей.** Пусть R — резервы, L = totalSupply × P, V — стоимость выкупаемых токенов. Из резерва уходит k·V (k = 1,2 на FULL, 1,0 на STANDARD), а стоимость отданного стейбла по min(p, $1) не больше этой суммы. Тогда (R − kV) / (L − V) ≥ R / L, если k ≤ R / L. На FULL: k = 1,2 < 1,4 ≤ R/L. На STANDARD: k = 1,0 < 1,15 ≤ R/L. Значит, любой разрешённый выкуп покрытие только повышает. Это проверяют fuzz-тест `testFuzz_RedeemNeverLowersCoverage` и stateful-инвариант `invariant_RedeemNeverLowersCoverage` (см. AUDIT_REPORT.md).

**Откуда берётся покрытие ≥ 140%.** Сразу после минта покрытие около 120%, то есть уровень STANDARD. Выше 140% оно поднимается так:
1. Индекс или рабочая цена падают. Например, при индексе $0,85 покрытие 120% / 0,85 ≈ 141%. С v0.4 из $1 туда можно попасть только за два месяца ($1 → $0,89 → $0,85), потому что за одно обновление индекс меняется не более чем на 11%. По той же причине одним `setIndex` нельзя перейти напрямую из FULL в SUSPENDED и обратно: 140/115 ≈ 1,217 > 1,11.
2. Копятся буферы: каждый выкуп на STANDARD оставляет в резерве 20% от стоимости выкупленных токенов. Пример из тестов: трое по $1000; после двух выкупов покрытие около 160%, и третий получает залог с буфером.
3. Резерв пополняют без минта через `topUpReserve(basketId, stable, amount)`. Вызвать может кто угодно (владелец, казна, спонсор), токены не выпускаются. Это работает и на паузе. Пополнение только повышает обеспечение. Выгоды тому, кто пополнил, оно не даёт: добавленные 20% делятся между всеми держателями, а цикл «минт → выкуп» на FULL убыточен из-за двух комиссий по 0,3% (fuzz `testFuzz_MintThenFullRedeemNotProfitable`).

Покрытие снижают рост индекса или рабочей цены, падение цены стейбла ниже $1 и новые минты (каждый добавляет обеспечение ровно 120%).

**События для уведомлений.** `CoverageTierChanged(basketId, oldTier, newTier, coverageBps)` — первые три поля индексированы, выпускается *только* при фактической смене уровня после `mint`, `redeem`, `topUpReserve`, `setIndex`, `setWorkingPrice`, `setManualPrice`, `setStableFeed`, `pokeTier`, `pokeStable`. Цена во внешнем фиде меняется без транзакции в Vault, поэтому есть `pokeTier(basketId)` и `pokeStable(stable)` — их может вызвать кто угодно (бот по расписанию). Бот подписывается на фильтр `newTier = 2` (Full) и рассылает уведомление «теперь можно выкупить с резервом». Последний известный уровень — `lastTier(basketId)`, статус депега — `lastDepegged(stable)`. Значения уровней: 0 — Suspended, 1 — Standard, 2 — Full. Полный список событий — раздел 4.

**Котировка для сайта (до транзакции).** `quoteRedeem(basketId, stable, tokens)` возвращает:
- `tier` — текущий уровень;
- `coverageBps` — текущее покрытие;
- `payoutNow` — сумма сейчас, после комиссии; 0, если выкуп приостановлен;
- `feeNow` — комиссия при выкупе сейчас;
- `payoutWithBuffer` — сумма, которую пользователь получил бы на уровне FULL;
- `reserveAvailable` — резерв выбранного стейбла;
- `executableNow` — пройдёт ли выкуп прямо сейчас: нет паузы, нет депега, уровень не SUSPENDED, резерва хватает.

`previewRedeem` возвращает `payoutNow` и `feeNow`.

**Пример мягких текстов для сайта** (подставляются значения из `quoteRedeem`):
- STANDARD: «Сейчас вы можете получить **{payoutNow} {стейбл}**. Если немного подождать, когда обеспечение корзины вырастет до 140% (сейчас {coverageBps/100}%), выкуп пройдёт вместе с резервом — **{payoutWithBuffer} {стейбл}**. Хотите, мы пришлём уведомление, когда это станет возможно? Выкупить сейчас тоже можно — решать вам.»
  Кнопки: «Уведомить меня» / «Выкупить сейчас за {payoutNow}».
- FULL: «Отличные новости: сейчас выкуп проходит вместе с резервом. Вы получите **{payoutNow} {стейбл}**.»
- SUSPENDED: «Выкуп временно приостановлен: обеспечение корзины ({coverageBps/100}%) ниже 115%. Ваши токены в безопасности, и выкуп откроется автоматически, как только обеспечение восстановится. Мы можем сообщить вам об этом.»

Защита пользователя: параметры `minTokensOut` и `minStableOut` (slippage). Есть функции предпросмотра `previewMint`/`previewRedeem` и показатель `collateralRatioBps(basketId)`.

## 4. События
Каждое изменение состояния выпускает событие (↑ — indexed). Покрытие — в bps; `type(uint256).max` означает «supply = 0».

| Действие | Событие и параметры |
|---|---|
| Деплой | `OwnershipTransferred(0↑, owner↑)`, `FeeRecipientUpdated(0↑, recipient↑)`, `MinMintUpdated(0, value)`, `StableAdded(USDT/USDC↑, 6, feed↑=0, 0, viaTimelock=false)` |
| Создание корзины | `BasketAdded(basketId↑, token↑, initialIndex, initialTier)` |
| Индекс (28-го) | `IndexUpdated(basketId↑, oldIndex, newIndex, oldWorkingPrice, year, month, timestamp)` |
| Рабочая цена | `WorkingPriceUpdated(basketId↑, oldPrice, newPrice, index)` |
| Смена уровня | `CoverageTierChanged(basketId↑, oldTier↑, newTier↑, coverageBps)` |
| Пауза | `Paused(account)` / `Unpaused(account)` (OpenZeppelin) |
| Стейбл: заявка | `StableProposed(stable↑, decimals, feed↑, maxFeedStaleness, executeAfter, previousExecuteAfter)` |
| Стейбл: отмена | `StableProposalCancelled(stable↑, executeAfter)` |
| Стейбл: включение | `StableAdded(stable↑, decimals, feed↑, maxFeedStaleness, viaTimelock=true)` |
| Минимальный минт | `MinMintUpdated(oldValue, newValue)` |
| Минт | `Minted(basketId↑, user↑, stable↑, stableIn, fee, tokensOut, workingPrice, stablePrice, tier, coverageBefore, coverageAfter)` |
| Выкуп | `Redeemed(basketId↑, user↑, stable↑, tokensIn, stableOut, fee, workingPrice, stablePrice, tier, coverageBefore, coverageAfter)` |
| Пополнение | `ReserveToppedUp(basketId↑, from↑, stable↑, amount, coverageBefore, coverageAfter)` |
| Казна | `FeeRecipientUpdated(old↑, new↑)` |
| Ручная цена | `ManualPriceUpdated(stable↑, oldPrice, newPrice)` |
| Фид | `StableFeedUpdated(stable↑, oldFeed, newFeed, oldMaxStaleness, newMaxStaleness)` |
| Депег вкл/выкл | `StableDepegStatusChanged(stable↑, depegged, price)` — когда переход обнаружен в транзакции: `setManualPrice`, `setStableFeed`, `executeStable`, `pokeStable`, `pokeTier`, `topUpReserve`, а также успешные `mint`/`redeem` (только выход из депега: в депеге они ревертятся, и событие откатилось бы) |
| Владелец | `OwnershipTransferStarted(prev↑, new↑)`, `OwnershipTransferred(prev↑, new↑)` (Ownable2Step) |

Порядок событий в одной транзакции: `StableDepegStatusChanged` → основное событие → `CoverageTierChanged`. Ревертнутые вызовы событий не оставляют. Поля `Minted`/`Redeemed` передаются во внутреннюю функцию одной memory-структурой `OpLog`. Без этого компилятор выдаёт `Stack too deep` (проверено: и с оптимизатором, и без него). `via_ir` сознательно не включён: он меняет кодогенерацию всего контракта, а у `forge coverage` есть ограничения с via-IR.

## 5. Допущения
1. Выкуп трёхуровневый, по решению Антона (см. раздел 3). Пороги 140% и 115% — константы. Чтобы их изменить, нужен новый деплой; так владелец не может ни незаметно закрыть выкуп, ни открыть выкуп с буфером.
1a. Пороги включают границу: ровно 140,00% — уже FULL, ровно 115,00% — уже STANDARD. Покрытие считается в bps с округлением вниз.
2. «28-е число» считается по UTC. Если 28-го обновление пропущено, следующее возможно только 28-го числа следующего месяца.
3. Стартовый индекс задаётся в `addBasket` без правила 28-го числа.
4. Изменение индекса 28-го числа ограничено ±11% от предыдущего зафиксированного индекса (v0.4). Правило ±3% для рабочей цены считается от нового индекса. Лимит ограничивает один шаг, но не накопленное изменение: за 2 месяца ×1,2321 / ×0,7921, за 6 — ×1,8704 / ×0,4970, за 12 — ×3,4985 / ×0,2470.
5. Ручная цена стейбла по умолчанию $1. Ответ фида принимается, только если одновременно: вызов `latestRoundData` успешен и вернул ≥ 160 байт; `answer > 0` и ≤ 2^128−1; `updatedAt ≠ 0`, не в будущем и не старше `maxFeedStaleness`; `answeredInRound ≥ roundId`; `decimals()` успешен и ≤ 18. Вызовы фида идут через `staticcall` с лимитом газа 100 000 и фиксированным буфером ответа (защита от return-bomb). Иначе берётся ручная цена. Все цены (индекс, рабочая, ручная) должны быть в диапазоне (0, 10^36] (`InvalidPrice`).
6. Стейблы с комиссией за перевод учитываются по фактически полученной сумме. Стейблы с decimals > 18, ребейзящиеся токены и токены с хуками (ERC777) не поддерживаются: добавлять такие стейблы через таймлок нельзя (хук-токены протестированы на реентрантность, но не рекомендуются). Один `BasketToken` можно привязать только к одной корзине (`TokenAlreadyRegistered`). Казна не может быть нулевым адресом или самим Vault.
7. Выкуп возможен в любом разрешённом стейбле, но не больше его резерва в этой корзине.
8. Минимального выкупа нет. Все округления — в пользу протокола: токены и выплата — вниз, комиссия — вверх . Пример (USDT, P = $1, STANDARD): выкуп 1e12 wei токена даёт gross = 1 wei, комиссия = 1 wei, выплата 0 → `ZeroAmount`; выкуп 2e12 wei — выплата 1 wei, комиссия 1 wei. Нулевой результат минта/выкупа и нулевая сумма в `mint`/`redeem`/`topUpReserve` ревертят `ZeroAmount`.

## 7. Риски
- **Централизация.** Один ключ owner'а — это оракул, пауза и все параметры. При компрометации ключа можно в пределах правил сдвигать индекс на ±11% каждый месяц (за год до ×3,50 или ×0,25) и заблокировать вывод паузой. Рекомендуются multisig (Safe) и таймлок.
- **Ручная цена депега приблизительна.** Она обновляется только когда owner отправит транзакцию, поэтому между реальным депегом и блокировкой возможна задержка, и в это окно можно минтить. Фид Chainlink с fallback уменьшает эту задержку, но не убирает её.
- **Очередь на выкуп.** На STANDARD тем, кто выкупает раньше, выгоднее ждать: каждый ранний выкуп оставляет буфер следующим. Возможен эффект «все ждут 140%». И наоборот: при падении ниже 115% выкуп закрывается для всех, пока покрытие не восстановится.
- **Уровень может измениться между котировкой и транзакцией** (новый индекс, другие выкупы). От этого защищает `minStableOut`; сайт должен передавать его по `payoutNow`.
- **События не появляются сами при движении фида**: нужен вызов `pokeTier`/`pokeStable` (бот). Расчёт покрытия перебирает все стейблы, поэтому газ растёт с их числом.
- **Резервы по стейблам разные.** Если все выкупают в одном стейбле, его резерв может закончиться раньше, чем резерв другого.
- Контракт не прошёл внешний аудит; внутренняя проверка и её ограничения — в `AUDIT_REPORT.md`, сырые результаты — в `test-results.txt`.

## 10. Изменения v0.4
- В `setIndex` добавлен жёсткий лимит: новый индекс должен быть в пределах ±11% от предыдущего зафиксированного индекса корзины. Константа `MAX_INDEX_CHANGE_BPS = 1100`, owner её не меняет.
- Границы включительны и округляются в сторону строгости. Пример: при old = 1e18 + 7 wei
  - min = 0,89e18 + 7 (точное значение 0,89e18 + 6,23 округлено вверх);
  - max = 1,11e18 + 7 (точное 1,11e18 + 7,77 округлено вниз).
- Порядок проверок в `setIndex`:
  1. корзина существует;
  2. `InvalidPrice`;
  3. `NotIndexDay`;
  4. `IndexAlreadyUpdatedThisMonth`;
  5. `IndexChangeTooLarge`.

  Отказ по лимиту не меняет состояние, поэтому месяц остаётся доступным.
- Новая ошибка: `IndexChangeTooLarge(uint256 basketId, uint256 oldIndex, uint256 newIndex, uint256 minAllowed, uint256 maxAllowed)`.
- Новая view-функция: `indexBounds(basketId) → (minAllowed, maxAllowed)`. По ней сайт или бот может проверить значение до транзакции.
- Стартовый индекс корзины (`addBasket`) по-прежнему лимитом не ограничен. Первое `setIndex` новой корзины ограничено уже от стартового индекса.
- События не менялись: `IndexUpdated` по-прежнему содержит oldIndex и newIndex.

### Ошибки `setIndex`
| Ошибка | Когда |
|---|---|
| `OwnableUnauthorizedAccount(account)` | вызывает не owner |
| `UnknownBasket(basketId)` | корзины нет |
| `InvalidPrice()` | `newIndex = 0` или `> 10^36` |
| `NotIndexDay(day)` | не 28-е число (UTC) |
| `IndexAlreadyUpdatedThisMonth()` | в этом месяце уже было успешное обновление |
| `IndexChangeTooLarge(basketId, oldIndex, newIndex, minAllowed, maxAllowed)` | новый индекс вне `[ceil(old×0,89), floor(old×1,11)]` |
