# 5. План перехода на мультисиг (Safe) и таймлок

Цель: убрать единый ключ (угрозы T1, T2, T10) и при этом не сломать правило «индекс — 28-го числа по UTC» и возможность быстрой аварийной паузы.

## 5.1. Проблема текущего контракта
У `BasketVault` одна роль `owner` на всё. Если поставить её за таймлок, задержка ляжет и на `pause()`. Тогда аварийная пауза
станет медленной. Если не ставить, `setStableFeed`, `setManualPrice`, `setFeeRecipient` останутся мгновенными.
Поэтому план идёт в два этапа: без изменения кода (этап A) и с разделением ролей (этап B, требует правки контракта и повторного аудита этой части).

## 5.2. Этап A — без изменения кода (можно на тестнете сразу)
1. Создать Safe на Base (app.safe.global): например **2 из 3** (Антон + два независимых ключа, один из них аппаратный).
   Порог и состав решает Антон.
2. Vault: `transferOwnership(SAFE)` → в Safe транзакция `acceptOwnership()`.
3. Токен: в Safe `grantRole(DEFAULT_ADMIN_ROLE, SAFE)` от текущего админа, затем текущий админ `renounceRole(DEFAULT_ADMIN_ROLE, self)`.
   Сначала проверить, что Safe действительно получил роль (`hasRole`).
4. Индекс 28-го: подписи собираются заранее (транзакция `setIndex` создаётся 26–27-го), исполнение — 28-го UTC. Порядок и проверки — `docs/OPERATIONS.md` §4 (вариант D).
5. Мониторинг событий (`IndexUpdated`, `WorkingPriceUpdated`, `ManualPriceUpdated`, `StableFeedUpdated`, `FeeRecipientUpdated`,
   `Paused`, `OwnershipTransferStarted`, `RoleGranted`) с оповещением всех подписантов.

Что даёт: компрометация одного ключа больше не даёт контроль. Чего не даёт: задержки, за которую пользователи успели бы выйти.

## 5.3. Этап B — разделение ролей + таймлок (изменение контракта, до основной сети)
Предлагаемая схема (OpenZeppelin `AccessControl` + `TimelockController`):

| Роль | Функции | Держатель | Задержка |
|---|---|---|---|
| `PAUSER_ROLE` | `pause()` | Safe «аварийный» (низкий порог, например 1 из 3) + бот-сторож | нет |
| `UNPAUSER` / `ADMIN` | `unpause()`, `setFeeRecipient`, `setMinMintUsd`, `setStableFeed`, `setManualPrice` (вне аварии), `addBasket`, `proposeStable` | `TimelockController` (proposer/executor — Safe 2 из 3) | 48–72 ч |
| `ORACLE_ROLE` | `setIndex`, `setWorkingPrice` | Safe 2 из 3 напрямую **или** через таймлок 48 ч (заявка 26-го, исполнение 28-го) | 0 или 48 ч |
| `DEPEG_GUARD` | `setManualPrice` только **вниз** (объявить депег) | аварийный Safe | нет |
| Админ ролей токена | `grantRole(MINTER_ROLE)` | тот же `TimelockController`; после настройки — рассмотреть `renounceRole` | 48–72 ч |

Дополнительно (по желанию, тоже правка кода):
- максимальная длительность паузы или автоматическое снятие через N дней — чтобы пауза не превращалась в блокировку выхода;
- годовой потолок накопленного изменения индекса (R-2b);
- публикация хеша исходных данных индекса в событии `IndexUpdated` (раздел 3.4);
- проверка L2 sequencer uptime feed для Base mainnet (R-4).

### Совместимость таймлока с правилом 28-го
`TimelockController.schedule` задаёт минимальную задержку, а `execute` можно вызвать в любой момент после неё.
При задержке 48 ч заявка ставится 26-го в 00:00 UTC или позже, исполняется 28-го (окно 00:00–23:59 UTC = 07:00 28-го – 06:59 29-го по Вьетнаму).
Если исполнение не попало в 28-е, `setIndex` ревертится (`NotIndexDay`), заявку нужно ставить заново на следующий месяц.

## 5.4. Порядок работ
1. Решение Антона: состав и порог Safe, задержки, нужен ли этап B до основной сети.
2. Этап A на тестнете (Base Sepolia) — проверить всю процедуру ежемесячного обновления через Safe.
3. Если выбран этап B — изменить контракт, тесты, **зафиксировать новый коммит для аудита** (изменение scope и цены).
4. Аудит (раздел 6), исправления, повторная проверка.
5. Основная сеть: деплой → права сразу на Safe/таймлок → публикация адресов и процедуры.
